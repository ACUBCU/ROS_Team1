## 1. "팔이 출발 자리에 도착하지 못해서 중단합니다" — joint2가 한계선에 걸림

**증상**: 어제까지 잘 되던 픽앤플레이스가 오늘 "도착 못함" 에러로 계속 중단됨.

**원인**: `config/box_slots.yaml`의 4개 자리 모두 joint2 값이 정확히 **0.85**로 저장돼 있었는데, `CLAUDE.md`에 이미 기록된 대로 이 팔은 joint2 ≈ 0.85rad가 "겨우 닿는" 한계선입니다. 재시도(`max_retries=3`)로 어찌어찌 수렴하던 게, 시스템 부하가 조금만 높아져도 3번 안에 허용 오차(`POSITION_TOLERANCE=0.03`) 안으로 못 들어와서 실패로 처리됨.

**잘못 시도했던 방법**: joint2를 0.85 → 0.78로 낮춰서 여유를 줌. 이동 자체는 성공했지만, 검증됐던 실제 집기 위치가 틀어져서 **그리퍼가 박스를 헛손질하는 새 버그**가 생김(아래 2번).

**최종 해결**: joint2는 검증된 값 0.85로 되돌리고, 대신 `_move_and_wait()`의 `max_retries`를 3 → **6**으로 늘려서 좌표는 안 건드리고 수렴 기회만 늘림.

## 2. 그리퍼가 박스를 헛손질함 (joint2를 감으로 바꾼 부작용)

**증상**: "박스를 못 잡고 떨구었다."

**원인**: 위 1번에서 joint2를 0.78로 바꾸는 바람에, 실측으로 검증됐던 그립 위치(joint2=0.85 기준)가 미세하게 틀어짐. 로그의 `그리퍼 이동 성공: -0.00015` 같은 값이 "박스 표면에 닿아서 멈춘 정상 그립"인지 "허공을 닫아서 실패"인지 값만 봐서는 구분이 안 됐음(나중에 실제로는 대부분 정상 그립이었던 것으로 판명).

**교훈**: 검증된 물리 좌표를 감으로 다시 조정하지 말 것 — `CLAUDE.md`에 이미 적힌 원칙("관절 각도를 감으로 보내지 말 것")을 실제로 어겼다가 새 버그를 만든 사례. 좌표를 건드리는 대신 재시도 횟수처럼 안전한 파라미터를 조정해야 함.

## 3. 놓은 뒤 팔이 자리 위에 계속 머물러서 카메라가 박스를 못 봄

**증상**: 박스를 자리에 잘 놓았는데도 얼마 뒤 "빈 자리"로 잘못 표시됨. → 다음 명령이 "이미 있는데 없다고 착각"하거나 충돌 위험.

**원인**: `run_command()`가 박스를 놓은 뒤 팔이 그 자리 바로 위에 그대로 멈춰있어서, 천장 카메라가 방금 놓은 박스를 계속 못 봄. `OCCUPANCY_MISS_LIMIT`(10프레임) 넘게 연속으로 못 보면 "빈 자리"로 지워버리는 로직 때문에 실제로 박스가 있는데도 점유 현황에서 사라짐.

**해결**: 놓기(그리퍼 열기) 직후 `SAFE_LIFT_JOINT2` 높이로 들어올리는 5단계를 추가(`run_command()` 끝부분).

**한계**: 이 수정은 높이만 올릴 뿐 joint1(좌우 방향)은 그대로라서, 천장에서 완전 수직으로 내려다보는 카메라 시야는 여전히 부분적으로 가릴 수 있음. 필요하면 joint1도 살짝 옆으로 비켜주는 추가 개선이 남아있음.

## 4. `NameError: name 'target_joints' is not defined` — 위 3번 고치다 만든 버그

**증상**: 3번을 고친 뒤로 모든 이동이 박스를 놓는 데까지는 성공해놓고, 마지막 "비켜주기" 단계에서 매번 죽어버림. 그 바람에 "이동 완료" 로그가 세션 내내 단 한 번도 안 남았고, 3번에서 추가한 안전장치도 사실상 계속 작동을 안 하고 있었음.

**원인**: `_safe_move_to(target_joints, ...)`의 매개변수 이름인 `target_joints`를 `run_command()` 안에서도 그대로 쓸 수 있는 줄 알고 참조했는데, 실제로는 `run_command()` 스코프에 그 이름의 변수가 없었음(그 함수 안에서는 `self.slots[to_slot]["joints"]`로 접근해야 함).

**해결**: `to_joints = self.slots[to_slot]["joints"]`로 다시 조회해서 사용하도록 수정.

**교훈**: 코드를 고친 뒤 "에러 없이 로그가 정상적으로 찍히는지"까지 직접 확인해야 함 — 겉으로는 박스가 잘 옮겨지는 것처럼 보여도 마지막에 조용히 예외가 나면서 의도한 안전장치가 무력화될 수 있음.

## 5. "옮기다 놓쳤다" — 시스템 부하로 인한 타임아웃

**증상**: 박스를 쥐고 이동하는 도중 자리 점유 현황이 통째로 `{}`(빈 상태)로 찍히고, 곧이어 "팔 이동 결과를 못 받았습니다 (타임아웃)"이 뜸.

**원인**: `load average`가 6~8대로 상당히 높았음(Gazebo `gz sim server`가 CPU 183%까지 사용). `/joint_states`는 정상적으로 흐르고 있었지만, `FollowJointTrajectory` 액션의 결과 콜백이 부하 때문에 늦게 와서 `MOVE_TIMEOUT_SEC`(당시 35초) 안에 응답을 못 받은 것으로 추정 — `RUN_GUIDE.md`에 이미 기록된 "시스템 부하가 높을 때 실제로는 도착했는데도 콜백이 늦어서 타임아웃으로 오판" 현상과 일치.

**추가로 발견한 문제**: "다 끄고 처음부터" 재시작할 때 죽었어야 할 **예전 세션의 `robot_state_publisher` 프로세스가 안 죽고 남아있었음**(PID 패턴 매칭 kill이 다른 터미널 프로세스에는 안 먹힌 사례 — `CLAUDE.md`에 이미 문서화된 문제). PID로 직접 찾아서 정리함.

**해결**: `MOVE_TIMEOUT_SEC`을 35초 → **60초**로 늘림. 좀비 프로세스도 정리.

## 6. 박스 2개가 서로 자리를 바꿔야 하는 교착 상태

**증상**: 마커0을 1번 자리로 옮기려는데 "이미 마커1이 있어서 이동 불가", 마커1을 3번으로 옮기려는데 "이미 마커0가 있어서 이동 불가" — 서로 상대방 자리를 원하는 교착 상태.

**해결**: 빈 자리(4번)를 경유지로 써서 3단계로 풀었음: 마커1 → 4번(임시) → 마커0 → 1번 → 마커1 → 3번. `run_command()`는 두 자리를 직접 스왑하는 기능이 없으므로, 이런 상황에서는 항상 빈 자리를 하나 확보해서 우회해야 함.

## 7. 박스 원위치 복구는 로봇 팔 대신 Gazebo 텔레포트로

여러 번의 픽앤플레이스 테스트로 박스 2개가 원래 자리(마커0=1번, 마커1=3번)에서 계속 벗어나자, 로봇 팔로 하나하나 다시 옮기는 대신 **Gazebo의 `/world/empty/set_pose` 서비스로 박스 좌표를 직접 텔레포트**시키는 방법을 씀:

```bash
gz service -s /world/empty/set_pose --reqtype gz.msgs.Pose --reptype gz.msgs.Boolean --timeout 2000 \
  --req 'name: "aruco_cube_1", position: {x: 0.2001, y: 0.2001, z: 0.025}, orientation: {x: 0, y: 0, z: 0, w: 1}'
```

**주의**: 텔레포트 대상 좌표에 로봇 팔(특히 그리퍼)이 물리적으로 겹쳐 있으면, 텔레포트 자체는 성공해도 그 다음 물리 스텝에서 충돌이 발생해 박스가 다시 튕겨나갈 수 있음(실제로 한 번 겪음 — 팔이 그 자리 위에 파킹돼 있어서 박스가 공중 17cm까지 튕겨 올라감). **텔레포트 전에 반드시 그 좌표 위에 팔이 없는지 확인**하고, 있으면 먼저 비켜준 뒤 텔레포트할 것.

## 8. 사용자 요청: 최단경로(대각선 직행)로 변경

기존 `_safe_move_to()`는 (들어올리기 → 들어올린 채로 회전 → 내려놓기) 3단계로 나눠서 이동했음(다른 자리의 박스를 스치는 문제를 막기 위해 어제 도입한 안전장치, `HISTORY.md` 참고). 사용자가 "왜 빙그르르 돌아가냐, 최단경로로 가게 해달라"고 요청.

**트레이드오프를 먼저 설명**: 안전장치를 없애면 다른 자리에 박스가 있을 때 팔이 대각선으로 직행하면서 스칠 위험이 재발할 수 있음을 안내함.

**사용자 선택**: 그래도 최단경로로 변경 (속도 우선, 충돌 위험 감수).

**적용**: `_safe_move_to()`를 3단계 대신 목표 자세로 바로 `_move_and_wait()` 한 번만 호출하도록 단순화. 다른 자리에 박스를 배치해서 쓸 때는 이 트레이드오프를 염두에 둘 것.

## 9. 그런데도 "여전히 빙그르르 돈다" — joint1 하드웨어 한계였음

8번을 적용한 뒤에도 사용자가 "왜 자꾸 돌아가냐"고 재차 문의. 로그를 다시 분석해보니 실제로는 8번 수정이 정상 작동 중이었고(대부분의 자리 조합은 이미 직행), **2번 자리(135°)↔3번 자리(-135°) 조합에서만** 큰 회전(270도)이 발생하고 있었음.

**원인**: 이 코드는 목표 각도를 `target - current`로 그대로 계산해서 보내는데, 135°와 -135°는 앞쪽(0°)을 거치면 270도, 뒤쪽(±180°)을 거치면 90도로 갈 수 있음. 그런데 `open_manipulator_x_arm.urdf.xacro`를 확인해보니 **joint1의 물리적 회전 한계가 정확히 `-pi ~ +pi`(-180°~180°)** 로 못 박혀 있어서, 뒤쪽 90도 경로는 -180°/+180° 경계를 "타 넘어야" 하는데 이게 하드웨어 한계라 애초에 불가능함. 즉 이건 소프트웨어 버그가 아니라 조인트 하드웨어 한계 때문에 어쩔 수 없이 먼 길로 도는 것.

**다른 자리 조합은 이미 문제 없음** (1↔2, 1↔3, 1↔4, 3↔4는 각각 90/180/90/90도로 이미 최소 회전량).

**해결**: 사용자와 상의 후 "하드웨어 한계이니 그대로 둔다"로 결정. 이 조합(2번↔3번)을 자주 오갈 계획이라면, 자리 배치 각도를 45/135/-135/-45 대신 인접한 각도 조합(예: 0/90/180/-90)으로 바꿔서 이 조합 자체를 없애는 방법도 있음(단, 로봇 홈 자세와 겹치지 않는 각도를 골라야 함 — `CLAUDE.md`의 "자리를 로봇 기본 자세와 겹치는 각도에 두면 안 됨" 참고).

## 10. 자리 배치를 최종적으로 "카드널"(0/90/180/-90도)로 바꿈 — 그립 정렬이 진짜 핵심 문제였음

8~9번에서는 "2↔3번만 270도로 돈다"는 **이동 속도** 문제에 집중했었는데, 사용자가 진짜 문제를 짚어줬음: **모서리(45/135/-135/-45도) 배치로 접근하면 그리퍼가 박스 면이 아니라 모서리를 비스듬히 잡아서, 잡을 때마다 박스가 조금씩 돌아가고 이게 누적되다가 결국 못 잡거나 박스가 날아감.** joint1이 그리퍼의 world-frame 방향을 그대로 결정하는 구조라, 사각형 박스를 평평하게 잡으려면 joint1이 90도의 배수여야 함 — 카드널 배치가 정답이었음.

카드널로 바꾸면서 새로 발견/해결한 문제 2가지:

1. **0도가 로봇 홈 자세와 정확히 겹침** → `park_away_from_home()`으로 해결(위 참고).
2. **좌표가 정확히 한 축(x=0 또는 y=0) 위에 있으면 천장 카메라 인식이 실패하는 특이점을 발견함.** 처음엔 "카메라 화면비 때문에 ±90도 근처가 사각지대"라고 잘못 짐작했었는데, 실측으로 확인해보니 마커 종류·각도와 무관하게 **정확히 x=0 또는 y=0인 좌표에서만** 인식이 실패하고 3~5cm만 벗어나면 두 마커 다 정상 인식됨(원인은 특정 못함 - 아마 코너 검출 알고리즘이 축에 딱 걸린 대칭 케이스에서 흔들리는 것으로 추정). `empty_world.sdf`의 박스 기본 스폰 좌표에 일부러 y=0.02 오프셋을 줘서 회피함. 실제 로봇이 집어서 놓을 때는 항상 몇 cm 오차가 있어서 이 특이점에 걸릴 일이 거의 없음.

이 과정에서 자리 배치를 세 번(모서리→변의 중간 좁힌 버전→카드널) 시도해보면서 각 배치의 부작용을 전부 실측으로 확인함:
- 45/135/-135/-45(모서리): 그립이 박스 모서리를 잡아서 누적 오차로 결국 못 잡거나 날아감
- -90/-30/30/90(좁힌 변의 중간): 카메라 축 특이점 문제(당시엔 원인을 몰라서 "카메라 사각지대"로 오판)
- **0/90/180/-90(카드널, 최종 채택)**: 그립 정렬 문제 해결 + 홈 자세 겹침/좌표 특이점도 각각 해결함

`config/box_slots.yaml`과 `open_manipulator_bringup/worlds/empty_world.sdf`(git 저장소 밖) 둘 다 이 배치로 최종 반영됨.

## 11. 박스를 디폴트 위치로 되돌리는 버튼 추가

세션 내내 `gz service -s /world/empty/set_pose ...`를 터미널에서 직접 호출해서 박스 위치를 되돌렸는데, 이걸 웹 페이지 버튼으로 옮김. `web_control.py`의 `reset_boxes_to_default()`가 `subprocess`로 `gz service` CLI를 호출하고(로봇 팔은 안 건드림 - Gazebo 월드에 직접 요청), `/reset_boxes` 엔드포인트 + "박스 디폴트 위치로 되돌리기" 버튼으로 연결함. 좌표는 `DEFAULT_BOX_POSES`에 `empty_world.sdf`의 `<pose>`와 반드시 같은 값으로 하드코딩되어 있음 - world 파일의 기본 위치를 바꾸면 이 상수도 같이 바꿔야 함.
