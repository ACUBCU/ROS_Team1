## 1. 실물 로봇 + 실물 카메라 연결 (WSL USB 패스스루)

### 무엇을 했나
- 사용자가 실물 로봇(OpenManipulator-X)과 USB 웹캠(Logitech C920)을 컴퓨터에 연결
- 이 컴퓨터는 WSL(Windows 안의 리눅스)이라 USB 장치가 자동으로 안 보임 → **usbipd-win**이라는 Windows 도구로 "공유(bind) → 연결(attach)" 두 단계를 거쳐야 리눅스 쪽에서 보이게 됨
- 로봇은 `/dev/ttyUSB0`(시리얼), 카메라는 `/dev/video0`로 잡힘

### 겪은 문제
- 사용자가 실수로 **마우스**를 USB/IP로 연결해버려서 Windows에서 마우스가 안 먹히는 사고가 있었음 → `usbipd detach` 명령으로 바로 복구

## 2. 실물 카메라를 코드에서 직접 읽도록 바꿈

### 무엇을 했나
- Gazebo 시뮬레이션에서는 카메라가 `/gripper_camera/image_raw`라는 ROS 토픽으로 발행됐지만, 실물은 그런 토픽이 없음(그냥 USB 웹캠일 뿐)
- `person_follow_project.py`를 고쳐서, ROS 토픽 구독 대신 **OpenCV(`cv2.VideoCapture`)로 카메라 장치를 직접 읽도록** 바꿈 (`camera_timer_callback`)
- `cv_bridge`, `sensor_msgs/Image` 관련 코드를 전부 제거함(더 이상 필요 없어짐)

### 겪은 문제와 해결
- **화면이 가로로 심하게 깨짐(테어링)**: USB/IP로 가상화된 연결이라 대역폭이 실제 USB보다 훨씬 부족한 게 원인. 해상도를 낮추고(320x240 → 240x180 → **160x120으로 최종 정착**) MJPG 압축 포맷을 쓰니 완전히 해결됨.
  - 처음엔 "카메라만 단독으로 캡처 테스트"에서는 320x240도 멀쩡했는데, YOLO 추론+웹 스트리밍까지 같이 도는 **실제 사용 상황**에서는 계속 깨졌음 → 순간적인 테스트만으로는 충분히 검증이 안 된다는 교훈.

## 3. YOLO26을 "포즈(pose)" 모델로 바꿔서 진짜 얼굴(코) 추적

### 어떤 YOLO 모델을 썼나 (자세히)

[Ultralytics](https://www.ultralytics.com/)라는 회사가 만든 **YOLO26**이라는 최신 객체 인식 AI 모델을 씁니다. YOLO는 "You Only Look Once"의 줄임말로, 카메라 화면 한 장을 보고 "여기 사람이 있다, 여기 자동차가 있다" 하는 식으로 물체의 위치와 종류를 한 번에 찾아주는 AI입니다. 이미 수백만 장의 사진으로 미리 학습되어 있어서, 우리가 따로 학습시킬 필요가 전혀 없습니다(그냥 다운로드해서 바로 씀).

YOLO26에는 크기별로 여러 버전이 있는데(nano/small/medium/...), 우리는 가장 작고 빠른 **`yolo26n`**("n" = nano)을 씁니다 - 로봇에 딱히 강력한 GPU가 없어도 실시간으로 돌아가야 하기 때문입니다.

또한 YOLO26은 "무슨 일을 하는 모델이냐"에 따라 버전이 나뉘는데, 우리가 쓰는 건 그 중 **"포즈(pose) 추정"** 버전인 `yolo26n-pose.pt`입니다. 처음엔 그냥 "사람"이라는 네모 박스 하나만 알려주는 `yolo26n.pt`(기본 "탐지" 버전)를 썼었는데, 이러면 "사람이 여기 있다"까지만 알지 "얼굴이 정확히 어디냐"는 몰라서, 박스 크기 비율로 "대충 위쪽 15% 지점이 얼굴이겠지"하고 어림짐작해야 했습니다.

**`yolo26n-pose.pt`로 바꾸면**, 사람 한 명마다 온몸의 관절 **17개 지점**(코, 양쪽 눈, 양쪽 귀, 양쪽 어깨, 양쪽 팔꿈치, 양쪽 손목, 양쪽 골반, 양쪽 무릎, 양쪽 발목)의 정확한 좌표를 같이 알려줍니다. 이 중 **0번(코)** 좌표를 그대로 "얼굴이 정확히 어디 있는지"로 씀 - 어림짐작이 아니라 실제 얼굴 위치라 훨씬 정확합니다. 만약 사람이 뒤돌아 있어서 코가 안 보이면(모델이 "이 지점은 확신도가 낮다"고 알려줌), 예전처럼 박스 비율로 어림짐작하는 방식으로 자동으로 대체합니다.

### 요약
- 기존엔 `yolo26n.pt`(사람 박스만 줌)를 썼는데, **`yolo26n-pose.pt`**(사람 몸 관절 17개 좌표까지 같이 줌)로 바꿈
- 그 중 **코(nose) 키포인트**를 그대로 "얼굴 목표 좌표"로 씀 → 박스 비율로 어림짐작하던 것보다 훨씬 정확
- 코가 안 보이면(사람이 뒤돌아 있는 등) 기존 방식(박스 위쪽 15% 지점)으로 자동 대체

## 4. 실물 로봇에서 새로 겪은 문제들 (시뮬레이션과 다른 점)

1. **"충분히 가까움" 판정이 실물에서 아예 안 됨**: `GREET_BOX_HEIGHT=260`은 Gazebo의 480px 화면 기준값이었는데, 실물 카메라는 120px밖에 안 돼서 절대 도달 불가능했음 → 120px 기준으로 다시 계산(`70`).
2. **"사람을 보면 카메라가 바닥으로 감"**: 시뮬레이션의 거의 편 기본자세와 달리 실물 로봇 기본자세는 팔꿈치가 많이 굽어있어서, 같은 부호의 보정값을 더했을 때 반대 방향(아래)으로 움직였음 → `Y_GAIN` 부호를 반전해서 해결.
3. **탐색(사람 놓쳤을 때 찾기) 로직이 엉뚱한 방향으로 도망감**: 마지막으로 본 위치 쪽으로 방향은 맞게 잡아놓고도, 그 지점을 그냥 지나쳐서 반대쪽 끝까지 계속 가버림 → 마지막 위치 ± 좁은 범위(`LOCAL_SEARCH_RANGE`) 안에서만 왕복하도록 제한해서 해결.
4. **가구(의자)를 사람으로 오탐**: 확신도 문턱값(`CONF_THRESHOLD`)이 시뮬레이션 기준(0.2, 재탐색을 위해 낮춰뒀던 값)이라 너무 낮았음 → 실물 카메라는 매 프레임 다시 시도하니 0.5로 올려도 괜찮아서 올림.
5. **여러 사람이 잡히면 엉뚱한 사람을 쫓아감**: 확신도 기준으로 고르던 걸 → 박스가 가장 큰(=가장 가까운) 사람을 고르도록 변경.

## 5. GESTURE(손동작 조작) 모드 신설

### 무엇을 했나
- **MediaPipe의 손동작 인식 모델**(`gesture_recognizer.task`, 구글이 미리 학습시켜 공개한 모델 - 우리가 따로 학습 안 시켜도 됨)을 새로 추가
- 모드를 MANUAL → AUTO → **GESTURE** → MANUAL 순서로 순환하도록 확장 (`m` 키)
- 최종적으로 구현된 손동작:

| 손동작 | 동작 |
|---|---|
| 손바닥을 쫙 펴거나(Open_Palm) 주먹(Closed_Fist) | 정지 |
| 엄지손가락이 가리키는 방향 | 그 방향으로 팔이 조금씩 이동 (joint1=좌우, joint2~4=상하) |
| 손가락 2개(검지+중지) | 그리퍼를 조금씩 계속 열기 (자세 유지하는 동안 계속, ~1초에 완전히 열림) |
| 손가락 3개 | 그리퍼를 조금씩 계속 닫기 |
| 손가락 4개 | 디폴트 자세로 이동 |

- 화면에 손목→엄지 화살표, 손가락 개수(`fingers=N`), 인식된 동작 이름을 실시간으로 그려서 "인식이 되는지 안 되는지" 눈으로 바로 확인 가능하게 함

### 손가락 개수는 어떻게 세나 (자세히)

MediaPipe의 손동작 인식 모델은 손 하나마다 **손 마디(landmark) 21개**의 좌표를 줍니다(손목 1개 + 손가락 5개 × 4마디). 각 손가락은 뿌리(MCP) → 중간(PIP) → 끝(TIP) 순서로 3~4개의 관절 좌표가 있습니다.

MediaPipe 자체에 "지금 손가락이 몇 개 펴져 있는지" 알려주는 기능은 없고(“Open_Palm”, “Victory”처럼 정해진 몇 가지 손동작 이름만 줌), 그래서 **직접 세는 코드를 짰습니다**:

1. 검지, 중지, 약지, 새끼손가락 4개에 대해(엄지는 움직이는 방향이 달라서 제외)
2. 각 손가락의 "끝(tip)" 좌표가 "중간 마디(pip)" 좌표보다 **손목에서 더 멀리 떨어져 있으면** → 그 손가락은 "펴짐"으로 판단
   - 손가락을 펴면 끝부분이 손목에서 쭉 뻗어나가 더 멀어지고, 손가락을 접으면 끝부분이 손바닥 쪽으로 말려 들어와 손목과 오히려 더 가까워지는 원리를 이용함
3. 4개 중 몇 개가 "펴짐"인지 그냥 개수를 셈 (0~4)

이 방식은 손이 화면에서 어느 각도로 돌아가 있어도(손을 옆으로 기울이거나 살짝 돌려도) 비교적 안정적으로 잘 맞습니다 - "손가락 끝이 손목에서 먼가 가까운가"라는 상대적인 거리 비교라서, 손 전체가 회전해도 그 관계 자체는 잘 안 바뀌기 때문입니다.

### 시행착오
- 처음엔 "검지 세우면 열기, 브이하면 닫기"로 만들었다가 → "손바닥/손등 방향으로 브이 하나로 열기/닫기 구분"으로 바꿨다가(인식이 잘 안 됨) → 최종적으로 **손가락 개수(2개/3개)로 구분**하는 방식이 가장 안정적이어서 이걸로 정착함.
- **진짜 버그 1개 발견**: 그리퍼 액션이 "거절(rejected)"되는 경우를 처리 안 해서, 한 번이라도 거절당하면 `gripper_goal_in_progress` 플래그가 영원히 `True`로 남아 그 뒤로 모든 그리퍼 명령이 조용히 씹히는 문제가 있었음(로봇 팔 쪽 코드엔 이미 있던 처리를 그리퍼 쪽엔 빠뜨렸었음). 발견해서 수정함.

## 6. 그리퍼가 물리적으로 안 움직이던 문제 — 원인 찾고 해결함

**증상**: 그리퍼 액션에 목표를 보내면 "성공"으로 응답은 오는데 실제 위치(`/joint_states`의 `gripper_left_joint`)가 전혀 안 바뀜.

**진짜 원인**: 그리퍼 모터나 배선 문제가 아니었음. GESTURE 모드가 명령을 너무 자주(약 100~300ms 간격) 보내면서, USB/IP로 가상화된 시리얼 연결(`/dev/ttyUSB0`)의 대역폭을 넘어서 `SYNC_READ_FAIL` 통신 에러가 쌓였고, 결국 `controller_manager`가 `arm_controller`, `gripper_controller`, `joint_state_broadcaster`를 전부 `inactive`로 내려버림. 로그에 "Can't accept new action goals. Controller is not running."이 반복 출력된 걸로 확인함.

**해결**:
1. bringup(로봇 구동 프로세스)을 완전히 재시작
2. `INFER_EVERY_N_FRAMES`를 1 → 3으로 올려서 YOLO 추론(=팔 이동 명령 빈도)을 1/3로 줄임 → 시리얼 통신 부하를 줄여서 컨트롤러가 다시 안 죽게 함

**재시작 후 직접 테스트로 확인**: 그리퍼를 0.019(코드상 OPEN 값)로 보내니 실제로 열렸고, -0.01(코드상 CLOSE 값)로 보내니 실제로 닫혔음(사용자가 눈으로 직접 확인). 즉 `GRIPPER_OPEN = 0.019`, `GRIPPER_CLOSE = -0.01` 값은 처음부터 방향이 맞았고, 반대로 바꿀 필요 없음.

## 오늘 최종 변경 사항 정리 (`person_follow_project.py`)

- 카메라: `cv_bridge`/ROS 토픽 → `cv2.VideoCapture` 직접 사용, 160x120 @ 10fps
- YOLO 모델: `yolo26n.pt` → `yolo26n-pose.pt` (코 키포인트 활용)
- `Y_GAIN`: 부호 반전 (실물 기본자세 차이 때문)
- `GREET_BOX_HEIGHT`: 260 → 70 (실물 카메라 해상도 기준)
- `CONF_THRESHOLD`: 0.2 → 0.5 (오탐 방지)
- `LOCAL_SEARCH_RANGE` 신설: 탐색이 마지막 위치 근처에서만 왕복하도록 제한
- `SEARCH_HOLD_FRAMES` 신설: 탐색 중 마지막 위치 도착 직후 몇 프레임 더 확인
- `JOINT_LIMITS_SAFE` 신설: ROBOTIS 하드웨어 한계에서 5도씩 여유를 둔 안전 범위, 모든 이동에 항상 적용
- `GESTURE` 모드 신설: `gesture_callback()`, `_count_extended_fingers()`
- `reset_to_default()` 신설: 실물 bringup 직후 자동으로 잡는 자세로 되돌리는 기능 (웹뷰 버튼 + 손가락 4개 동작)
- 그리퍼 액션 거절 처리 버그 수정 (`gripper_goal_callback`)
- 웹뷰(`web_control_person.py`): GESTURE 모드 안내, 디폴트 위치 버튼, 원본 카메라 화면(박스/글자 없는) 추가
